description: Produces a self-contained standalone HTML mock (not production app code) for a full page (landing, marketing, blog, doc, sign-in, announcement), a section in isolation, or a single UI component. Two content modes — drafted (skill generates fill-in slots) or supplied (caller provides a file, attachment, or pasted text). Also owns iteration on a prior mock — "v2", "iterate on the hero", "tweak the mock", "change X", "update the layout". Trigger on mock / design / draft / sketch / prototype / render / show me what X looks like — applied to a page, section, or component — when there is no signal the output should ship inside a running application. Do NOT trigger when the request contains "in the app", "for the app", "in-app", "add to the site", or names a live route (those route to compose-app-surface). Do NOT trigger on stylesheet regeneration or auditing. Composes any page type whose shape rules are present in the reference; if a requested type's rules are absent it halts with SHAPE_RULES_PENDING rather than guess.

## What this skill does

Renders a single self-contained HTML file at a resolved output path. The mock inlines the generated stylesheet set and the theming + mode-resolution scripts so it opens correctly in any browser without external assets. Sections in isolation and components in isolation are wrapped in a minimal HTML page container so they render the same way. Iteration on a prior mock is handled in discovery — if a state record exists at the resolved output path, the prior `brief_snapshot` and `sections` are loaded and treated as the starting point.

## Inputs

- **From caller (runtime):** plain-language request; optional supplied content (file path, attached document, pasted text); optional output path override; optional asset paths.
- **From `$CUSTOMIZABLE_DESIGN_SYSTEM_ELEMENTS`:** the elements YAML — used indirectly through the generated stylesheet set; this skill does not re-read role bindings.
- **From the generated stylesheet set** (at `$CUSTOMIZABLE_DESIGN_SYSTEM_STYLESHEETS_DIR`): `tokens.css`, `components.css`, `themes.css`, and `manifest.json` for stale detection.
- **From shared reference (`../../reference/`):** `page-types.md`, `section-types.md`, `shapes.md` (named-shape catalog), `components.md`, `compliance.md`, and the foundations files — `foundations/overview.md`, `foundations/typography.md`, `foundations/layout.md`, `foundations/accessibility.md`, `foundations/motion.md`, `foundations/imagery.md`, `foundations/responsive.md`, `foundations/implementation.md` (§9 carries the theming + mode-resolution scripts inlined into the mock head).
- **From skill-local reference (`./reference/`):** `landing-sections-shape-rules.md` (defines `pick_shape` and shape-adjacency rules for landing pages). The Variety Principle and the background-color alternation schedule live in `../../reference/page-types.md` §20 (Primary Landing Page), not here.
- **From `$CUSTOMIZABLE_DESIGN_SYSTEM_MOCKS_DIR`:** default output directory for mocks.
- **From `$CUSTOMIZABLE_DESIGN_SYSTEM_ASSETS_DIR`:** default asset path when caller does not supply one.
- **From `$CUSTOMIZABLE_DESIGN_SYSTEM_INSTALL_MODE`:** decides whether state records go to `~/.claude/customizable-design-system/state/compose-page/` (global) or `<project-root>/.claude/customizable-design-system/state/compose-page/` (project).
- **From `$CUSTOMIZABLE_DESIGN_SYSTEM_EXTENSIONS_DIR`:** the project extensions directory — `shapes/`, `page-types/`, `section-types/`, each holding `*.md` definitions in the same shape as the plugin reference entries (basename = the canonical name). Project definitions are read **alongside** the plugin reference and **override it by name** (a project entry whose name matches a plugin entry replaces it wholesale), so a project grows the catalog without waiting on a plugin release.
- **From `../../lib/cds_hash.py`:** the shared fingerprint tool, used to detect a stale stylesheet set (the same hashes `generate-stylesheets` writes into `manifest.json`).

## Discovery checklist

The checklist runs in this exact order. Step 1 is the routing gate.

1. **Handoff check (FIRST).** Does the request include "in the app", "for the app", "to the app", "in-app", or name a live route? If yes → STOP `WRONG_SKILL:compose-app-surface` and instruct the caller (user or agent) to re-invoke as `/cds:compose-app-surface`. For requests without app language but where embedding is genuinely ambiguous, ask one question: "Is this a standalone mock or should it ship inside the live app?"
2. **State-directory check (iteration).** Resolve the candidate output path (from `$CUSTOMIZABLE_DESIGN_SYSTEM_MOCKS_DIR` or caller input or default). Look for a prior state record at strict-equality `output_path`. If found and the request reads as modification → load `brief_snapshot` and `sections` and treat as iteration. If found but the request reads as a fresh start → ask explicitly. If a new `output_path` is supplied but the request reads as iteration of an older path → ask: "There's no prior run at this output_path; I see a prior run at `{older-path}` — is this a fresh start, or a continuation with a new filename?"
   - **Update (brownfield) source check.** Distinct from iteration: if the caller supplies an EXISTING artifact to start FROM — an on-disk HTML file, an existing stylesheet, or a Figma reference/export — or uses update phrasing ("update the existing X", "from the repo", "from Figma", a Figma URL), enter the **UPDATE path** (see Pipeline): the supplied file(s) are the starting point and only the requested region is recomposed, leaving all other markup intact. Iteration starts from a prior CDS state record; update starts from external files. If neither applies, this is a fresh GENERATE.
3. **Page type.** For drafted content, ASK — do not infer. For supplied content, ASK with a suggested default based on observable signals (article-only content → editorial detail; landing-typical mix → landing) but let the caller pick.
4. **Surface kind.** Page, section, or component. Section and component get wrapped in a minimal HTML page container.
5. **Content mode.** Drafted (skill generates a fill-in markdown scaffold dynamically — asking only for slots the relevant section types and component types actually require, derived from `section-types.md` and `components.md`) OR supplied (caller provides a file path, attached document, or pasted text; skill reads it before composing).
6. **Asset paths.** Default from `$CUSTOMIZABLE_DESIGN_SYSTEM_ASSETS_DIR` if set, else ask.
7. **Mandatory / forbidden / leading elements.** Per `page-types.md` for the chosen page type, plus any caller overrides.
8. **Stylesheet freshness (auto-regenerate, never halt for staleness).** Compute the live input fingerprints — `python3 ../../lib/cds_hash.py inputs <$CUSTOMIZABLE_DESIGN_SYSTEM_ELEMENTS> ../../reference <$CUSTOMIZABLE_DESIGN_SYSTEM_EXTENSIONS_DIR|NONE>` — and read `manifest.json` at `$CUSTOMIZABLE_DESIGN_SYSTEM_STYLESHEETS_DIR`. If the manifest is missing, or any of `elements_semantic_sha256` / `reference_tree_sha256` / `extensions_tree_sha256` differs from the live value, the set is stale or absent → **invoke `generate-stylesheets` yourself** (load and execute `../generate-stylesheets/SKILL.md` against the live YAML + reference + extensions, writing to the stylesheets dir), then re-read the manifest and proceed. The YAML is the source, so a YAML change IS a stylesheet change — do not stop and ask the caller to regenerate by hand. Because the fingerprint is semantic, a comment- or `description:`-only YAML edit does **not** trigger a regeneration. If `generate-stylesheets` itself halts, STOP `STYLESHEETS_REGEN_FAILED:{inner-code}` surfacing the inner halt verbatim.

## Pipeline

1. **Load page-type rules (plugin + project extensions).** Read `../../reference/page-types.md` and `../../reference/section-types.md`, then overlay the project extensions dir — `$CUSTOMIZABLE_DESIGN_SYSTEM_EXTENSIONS_DIR/page-types/*.md` and `/section-types/*.md`. Build the working catalog as plugin-reference ∪ project-extensions, where a project definition whose name matches a plugin entry **replaces it wholesale** and project-only names extend the catalog. Identify the page-type entry for the chosen type and its mandatory / forbidden / leading constraints.
2. **Section sequence + shape derivation.** For **landing-page requests**, consult `./reference/landing-sections-shape-rules.md` and derive the ordered section sequence + a shape per section using its `pick_shape` and adjacency rules, applying the Variety Principle and the background-color alternation schedule from `../../reference/page-types.md` §20 (Primary Landing Page). Resolve shape names against the plugin `shapes.md` catalog overlaid with `$CUSTOMIZABLE_DESIGN_SYSTEM_EXTENSIONS_DIR/shapes/*.md` (project overrides plugin by name). **STOP `SHAPE_RULES_PENDING:{page-type}` only when the page type's shape rules are present in NEITHER the plugin reference NOR the project extensions — never guess.**
3. **Content resolution.** For supplied content, parse it into section candidates per `./reference/landing-sections-shape-rules.md` (or STOP per Step 2 for non-landing). For drafted content, generate the fill-in markdown scaffold dynamically — asking only for the slots the chosen section types and component types actually need, with slot definitions taken from `section-types.md` and `components.md`. Present the scaffold to the caller; wait for filled values before continuing.

   **Update path (brownfield).** When discovery selected the UPDATE path, do not compose from scratch. Instead: (a) read and parse the supplied existing artifact (on-disk HTML, an existing stylesheet, or a Figma reference resolved to markup) into a region map keyed by section landmarks / `data-shape` / headings — if it cannot be read or parsed → STOP `UPDATE_SOURCE_UNREADABLE`; (b) localize the target region(s) the change touches — if the change cannot be localized to specific region(s) → STOP `UPDATE_TARGET_AMBIGUOUS` and ask; (c) recompose ONLY the target region(s) through Steps 1–2 (the same shape/component pipeline, using the merged plugin+extension catalog); (d) splice the recomposed region back into the original document, leaving all other markup byte-for-byte intact. The remaining pipeline (compliance, sidecars, state record) runs on the spliced result; the sidecars cover the changed region.
4. **Render the mock.** Emit a single self-contained HTML file at the resolved output path. The `<head>` inlines `tokens.css`, `components.css`, `themes.css` (read from `$CUSTOMIZABLE_DESIGN_SYSTEM_STYLESHEETS_DIR`) inside a single `<style>` block, then inlines the theming + mode-resolution scripts from `../../reference/foundations/implementation.md` §9. For asset references in supplied content: inline as a `data:` URI when the file is readable from disk; if the reference is an absolute URL or an unreadable path, emit a warning to the caller but use the reference verbatim. **Do NOT embed agent-side metadata in the HTML** — no decision logs, no provenance comments, no structural maps. Build every component strictly to its `components.md` entry — do not improvise layout. In particular the **topbar follows §12.1**: logo alone at the left; `primary-nav` + `conversion-cta` grouped at the right (nav `margin-inline-start: auto`, or header `justify-content: flex-end` after the logo). Never center the nav, and never use `justify-content: space-between` on the topbar row. **Render each `primary-nav` item per §12.1:** a plain link, or — when the item has children — a §12.2 dropdown trigger (`aria-haspopup="menu"` + `aria-expanded`) plus its `role="menu"` panel in the chosen §12.2 variant (flat / mega / lift-and-scale), honoring the §12.2 keyboard contract (Arrow Up/Down between items, Enter/Space activate, Escape closes). In drafted content, ask for any nav items that should carry a dropdown and their child links.

   **Consume the design system's geometry — never re-invent component sizing in a page block.** Component sizing, spacing, radius, section padding, and container width come from the generated stylesheet tokens. The topbar logo height resolves from `--topbar-logo-height` and the bar from `--topbar-height` (both already in `components.css`) — do **not** add a page-block `.topbar-logo img { height: … }` or any rule that re-declares or overrides a system geometry token; the recurring topbar-logo defect was exactly this. For a **section wrapper** width use a section-wrapper token — `max-width: var(--container-marketing-primary)` (the page width, the default) or `.u-container-full` for full-bleed — never a `--column-*` reading width. A section wrapper's `max-width` is **≥ the page width, never below it** (`foundations/layout.md §11.2`); the `--column-*` reading widths (`--column-wide` / `--column-medium` / `--column-reading`) cap a **single inner content block** inside a page-width section, never the section wrapper. If a dimension you need does not exist as a token, the gap belongs in the YAML `geometry:` block (STOP and surface it), not in a page override. Page-block overrides of system-defined geometry are an `audit-against-system` violation (`compliance.md` §23 #18). **Render the logo per `components.md §12.1` and the `assets.logo` config:** the default single `currentColor` SVG glyph, or — when `assets.logo.mode == asset-pair` — two elements `<img class="logo-light">` and `<img class="logo-dark">` (data-URI-inlined per the asset rule, each at `--topbar-logo-height`) that the generated logo CSS selects by mode (`compliance.md` §23 #15).

   **Apply entrance motion through the generated classes, gated correctly every time.** Reveal, stagger, and fade entrances use the classes the design system already emits: `.reveal-word` (set `--reveal-index` per word), `.card-stagger` (set `--card-index` per card), `.content-fade` / `.content-fade-up` (add `.is-inview` via an `IntersectionObserver`). Do not author entrance `@keyframes` in a page block. Entrance motion **animates in the base rule** and is disabled **only** inside `@media (prefers-reduced-motion: reduce)` (the generated CSS already does this). **Never wrap hero word reveal, card stagger, or content fades in `@media (prefers-reduced-motion: no-preference)`** — that silently removes the entrance for reduce-motion users (`compliance.md` §23 #19, `foundations/motion.md` §15.4). `no-preference` is only for continuous/ambient enhancement (e.g. a looping marquee) whose static state is the no-animation baseline.
4a. **Emit companion sidecars (separate files, never in the HTML).** Beside the HTML at the resolved output path, write two sidecar files derived entirely from the resolved `sections` data (no new analysis):
   - `<basename>.wireframe.txt` — a labeled ASCII layout map, one block per section in order, each headed `T# · <section-type> · <shape> · <ground-role>` with an inner sketch of the shape's slots, so an unnamed section on the rendered page is identifiable at a glance.
   - `<basename>.decisions.md` — the step-by-step composition reasoning: a `## T# <section>` block per section recording the chosen shape and the `pick_shape` trigger (the `content_meta` that selected it, alternates rejected), the ground / background-alternation reasoning, the section width, and any motion or override notes.

   These are SEPARATE files; the HTML stays metadata-free (the Compliance gate still forbids agent-side metadata inside the HTML).
5. **Component- or section-in-isolation wrapping.** Wrap the isolated piece in a minimal HTML page container: viewport meta tag, `<html>` / `<body>`, light-mode default with a top-right mode toggle, 1440px viewport content width, 64px outer padding.
6. **Compliance pass.** Validate against `../../reference/compliance.md` rules tagged `[scope: standalone]` and `[scope: both]`. Any failure → fix in place; if a rule cannot be satisfied without violating a reference spec → STOP `PRECONDITION_FAILED` with the rule citation.
7. **Write the state record.** Append one YAML file named `{ISO-timestamp}-{output-basename}.yaml` to the resolved state directory using the shared state-record schema, including the two sidecar paths from Step 4a, `mode` (`generate` | `update`), and — for updates — `update_source` (the path or Figma ref the change started from) and a per-section `preserved` flag. Retain the last 10; delete older records after writing. (The `package-change` skill reads these fields to assemble the hand-off bundle.)

## Halt conditions

- `STYLESHEETS_REGEN_FAILED:{inner-code}` — the stylesheet set was stale or missing and the auto-invoked `generate-stylesheets` itself halted; the inner halt code is surfaced verbatim.
- `SHAPE_RULES_PENDING:{page-type}` — the requested page type's shape rules are present in NEITHER the plugin reference NOR the project extensions dir.
- `MISSING_SPEC` — a required spec is too thin to render and is absent from both the plugin reference and the project extensions (name the gap).
- `MISSING_COMPONENT:{name}` — a required component is not defined in `../../reference/components.md`.
- `UPDATE_SOURCE_UNREADABLE` — the existing artifact supplied for a brownfield update cannot be read or parsed.
- `UPDATE_TARGET_AMBIGUOUS` — an update request cannot be localized to a specific region.
- `OUTPUT_PATH_UNRESOLVABLE` — no output path provided and none discoverable.
- `PRECONDITION_FAILED` — compliance rule cannot be satisfied against the resolved reference.
- `ELEMENTS_YAML_UNSET` — `$CUSTOMIZABLE_DESIGN_SYSTEM_ELEMENTS` not set.
- `WRONG_SKILL:{name}` — the request belongs to a different skill (e.g., `compose-app-surface` when app-embedding language is present); the caller must re-invoke the correct skill or slash command.

Halt surface format:

```
STOP: compose-page: {halt-code}: {one-line summary}

Reference: {file:line or section pointer}
Detail: {one paragraph explaining what is needed to proceed}
```

Iteration with an unreadable prior state record → STOP and ask the caller whether this is a fresh start or supply the prior brief.

Supplied content unreadable or unparseable → STOP and ask the caller for an alternate path or paste.

## Compliance gate

The emitted mock must satisfy every rule tagged `[scope: standalone]` and every rule tagged `[scope: both]` in `../../reference/compliance.md`. The mock must NOT contain agent-side metadata (no decision logs, no provenance comments, no structural maps).

## Boundary — does not

- Does not emit production-app code, framework-native components, or app shell wiring — `compose-app-surface` owns that.
- Does not inspect host-project code, naming, tokens, or patterns.
- Does not itself author stylesheet CSS; when the inputs have moved it INVOKES `generate-stylesheets` to refresh the set, then proceeds — `generate-stylesheets` still owns CSS authoring.
- Does not embed agent-side metadata in the emitted HTML; the wireframe and decision-log sidecars are SEPARATE files (Step 4a), never inlined into the HTML.
- Does not modify `$CUSTOMIZABLE_DESIGN_SYSTEM_ELEMENTS` or any file under `../../reference/`.
- Does not certify compliance after the fact — that is `audit-against-system`.
