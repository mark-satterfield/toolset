# cds — tests

Two kinds of test live here. Keep them distinct — they prove different things.

## 1. Deterministic tiers (`run-tests.sh`)

Pure scripts, no LLM. They prove the **configuration** is internally coherent for
whatever elements YAML is supplied — nothing is hardcoded.

```bash
./run-tests.sh                       # uses ../setup/customizable-design-elements.yaml
./run-tests.sh /path/to/other.yaml   # or any valid elements YAML
```

- **`check-plugin.py`** discovers and runs every `checks/check_*.py`
  (schema, structure, links, reference, consistency).
- **`../validation/lint-elements.py`** asserts properties: schema validity, every
  `var()` chain resolves, aliases target concrete themes, `from_palette` bindings
  land in allowed palettes, every required role is covered in every mode.

## 2. Visual render-proof (`render/`)

This tier answers the only question that matters for a design system: **does it
actually produce good UI?** It cannot be a script, because the thing under test is
the plugin's own skills. So it is generated by *running those skills*, then viewed.

```
render/
  styles/        tokens.css, components.css, themes.css, switcher.js, manifest.json, GAPS.md
                 — emitted by executing the generate-stylesheets skill on the live YAML
  components/    one real markup fragment per component family (53)
  shapes/        one pregenerated artifact per shape, S0–S28 (29)
  landing.html   a full sample landing page (alternating sections, variety principle)
  assemble.py    assembles the artifacts above into browsable galleries (a VIEWER only —
                 it generates no CSS or markup)
  index.html / components.html / shapes.html   the assembled galleries
  screenshots/   reference captures
```

**How the artifacts are produced** — the `cds-render-proof` workflow fans out across
sub-agents: one runs `generate-stylesheets`, others build the component fragments and
the shape artifacts, one composes the landing page. Everything is generated from the
**live** config and the reference tree — never a re-implementation.

**How to view** — `python3 render/assemble.py` then open `render/index.html` in a
browser. The theme/mode switch bar re-skins every page live. Each shape and component
is a real arrangement you can judge by eye — edit an artifact, re-run `assemble.py`,
re-view. That edit→render loop is the point: corrections come from seeing, not prose.

**Known gaps** — `render/styles/GAPS.md` lists everything the skills found too thin to
render fully (missing tokens, undefined roles, YAML defects). Gaps are a deliverable,
not a failure: they are the work list.

## Why nothing is committed pre-rendered as authoritative

A checked-in gallery is a snapshot of one configuration and goes stale the moment the
YAML changes. The artifacts under `render/` are regenerated from the live config; the
galleries are assembled on demand from those artifacts.
