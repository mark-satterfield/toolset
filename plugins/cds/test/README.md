# cds — tests

Three tiers prove three different things. The render proof is **not** optional —
a green run means structure **and** correctness **and** a real render proof exist.

## Deterministic tiers (`run-tests.sh`)

Pure scripts, no LLM. They prove the **configuration** is internally coherent for
whatever elements YAML is supplied — nothing is hardcoded.

```bash
./run-tests.sh                       # uses ../setup/customizable-design-elements.yaml
./run-tests.sh /path/to/other.yaml   # or any valid elements YAML
```

1. **`check-plugin.py`** discovers and runs every `checks/check_*.py`
   (schema, structure, links, reference, consistency, shape alignment, token coverage).
2. **`../validation/lint-elements.py`** asserts properties: schema validity, every
   `var()` chain resolves, aliases target concrete themes, `from_palette` bindings
   land in allowed palettes, every required role is covered in every mode.
3. **render proof** — `run-tests.sh` then requires the generated artifacts to exist
   and (re)assembles the galleries over them. If they are **absent it fails** (exit 1)
   — it never regenerates them itself (only the workflow can) and never lets a
   missing render proof pass silently.

## Visual render-proof

This tier answers the only question that matters for a design system: **does it
actually produce good UI?** It cannot be a script, because the thing under test is
the plugin's own skills. So it is generated by *running those skills*, then viewed.

All generated output lands in the **gitignored** `visual-proof-out/` — nothing
generated is ever committed:

```
visual-proof-out/        (gitignored — regenerated on demand)
  styles/        tokens.css, components.css, themes.css, switcher.js, manifest.json
                 — emitted by executing the generate-stylesheets skill on the live YAML
  components/    one real markup fragment per component family
  shapes/        one pregenerated artifact per shape, named with its semantic name
  landing.html   a full sample landing page (alternating sections, variety principle)
  index.html / components.html / shapes.html   the assembled galleries

assemble.py      committed tooling — assembles the artifacts above into browsable
                 galleries (a VIEWER only — it generates no CSS or markup; it
                 discovers themes from themes.css, modes from themes.css, and the
                 shape order/names from reference/shapes.md Part A, so it stays
                 correct for any config)
screenshots/     committed reference captures
```

**The single entry — `cds-render-proof` workflow.** Run it to do everything in one
pass: it **regenerates** (fans out across sub-agents — one runs `generate-stylesheets`,
others build the component fragments and the shape artifacts, one composes the landing
page), then **verifies** (runs the deterministic checks above), then **assembles** the
galleries. Everything is generated from the **live** config and the reference tree —
never a re-implementation. The shape list is read from `reference/shapes.md` Part A, so
shapes are never hardcoded.

**How to view** — after a workflow run (or `python3 assemble.py` to re-view existing
artifacts), open `visual-proof-out/index.html` in a browser. The theme/mode switch bar
re-skins every page live. Each shape and component is a real arrangement you can judge
by eye — edit an artifact, re-run `assemble.py`, re-view. That edit→render loop is the
point: corrections come from seeing, not prose.

## Why nothing is committed pre-rendered as authoritative

A checked-in gallery is a snapshot of one configuration and goes stale the moment the
YAML changes. The artifacts in `visual-proof-out/` are regenerated from the live config
and gitignored; the galleries are assembled on demand from those artifacts. The only
committed pieces are the *tooling* (`assemble.py`, the checks) and the *reference*
captures (`screenshots/`) — never the generated output.
