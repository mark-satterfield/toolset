# agent-teams-workforce — workflow scripts

These are the **canonical source** for the agent-teams-workforce pipelines: the deterministic `Workflow` scripts that orchestrate the agents in `../agents/`. The agents declare *what* they do; these scripts decide *when* each runs, how work is routed, and where the deterministic control flow ends and agent judgment begins.

## Status: canonical here, deployed by hand (for now)

The Claude Code plugin framework does not deploy workflows natively, so these do not ship to a project automatically the way agents and skills do. Deployment will be **automated** — a `SessionStart` hook will symlink this folder into a consuming project at `.claude/workflows/agent-teams-workforce-pipelines/` and refresh it when the plugin version changes.

Until that automation lands:

- **This folder is the single source of truth.** Edit workflows here, not in a consuming project.
- **Changes must be copied to consuming projects by hand.** A project that already links or copies these scripts will not see an update until you re-copy (or the symlink target is refreshed).

## Contents

- **Composites** — `prd-to-spec.js`, `task-to-deploy.js`, `bug-fix.js`: full pipelines stitched from the pieces below.
- **Front-ends & phases** — `workspace.js`, `prd-reconciliation.js`, `prd-validation.js`, `architecture.js`, `repo-scoping.js`, `trd-authoring.js`, `spec-authoring.js`, `task-decomposition.js`, `suite-run.js`, `tdd-red.js`, `tdd-green.js`, `tdd-refactor.js`, `integration.js`, `adversarial.js`, `deploy.js`, `settle.js`, `documentation.js`, `infra-intent.js`, `deploy-mechanism.js`, `story-deploy-fix.js`, `built-version.js`.
  - `repo-scoping.js` rules the REPO SPAN of a PRD: the repositories its approved architecture delta changes. One polyrepo-steward session places each delta item (one element the delta shows, as `depscore.py arch-delta` lists it) in the repository whose code changes for it, or records that it has no code in this project, and creates each new repository the approved target names; a prerequisite item goes to the repository that deploys it or the one its closure entry names, and one an open bead plans is recorded as having no code here; the run fails when an item is placed twice or not at all, or a prerequisite against its closure entry.
  - `workspace.js` ESTABLISHES the worktree before the first write. Every code-writing composite dispatches it first, and its return value is the sole source of `contract.repoPath` — the caller supplies a repository, this step supplies the worktree. `task-to-deploy.js` keys it by the Task's Story, and stashes a reused tree's uncommitted changes, so a Story's Tasks share one worktree and one branch, cut from `main` when its first Task starts.
  - `settle.js` lands a tree in git — commit, push, PR — for `bug-fix.js`, on every exit path after deployment. With `commitOnly` it commits on the branch and stops: `task-to-deploy.js` commits each Task to its Story branch this way, after a final `suite-run.js` exits 0, and neither deploys nor opens a pull request.
  - `suite-run.js` runs the one test command the repository declares (its `AGENTS.md` or `CLAUDE.md`, or its Taskfile `test` task) and returns the exit code and the failing tests. `task-to-deploy.js` resolves it once at its baseline run and judges Red, Green, Refactor and the commit by it.
  - `deploy-mechanism.js` and `story-deploy-fix.js` are the agent steps of a Story's deploy, which the host runs when the Story's last Task is done. First a polyrepo-steward rules what the Story's repository publishes (a package to CodeArtifact, with the publish command the repository declares) and deploys (with CDK); the host stops a repository that does neither. Its scripts publish the package, then check the SSM parameters, `cdk deploy` and verify the stacks; on a failure `story-deploy-fix.js` has a `cdk-stack-author` fix the Story branch and run the synth assertion tests before the host tries again, a fix that changes no file stops the deploy, and the third failed attempt of a dispatch stops it. Once the deploy verifies, the host runs `built-version.js`: a `prd-reality-reconciler` compares the Story branch's code with the effective architecture and the Epic's delta items, writes each difference to `built/<subject>/`, and the `architecture-maintainer` corrects the effective version from it before the built views are removed. The host then opens the Story's one pull request and waits for GitHub to report it merged.
- **Portfolio** — three workflows over the Epics and Tasks, each runnable alone, sharing `../scripts/portfolio/depscore.py`:
  - `dependency-assessment.js` writes Epic dependency edges — architecture dependencies: which requirements an architecture decision is designed from first — and nothing else — for one new or changed Epic at a time: it reads that Epic's full PRD, searches the other Epics' PRDs for the ones related through an architecture decision the effective architecture leaves open, reads those in full, and writes only that Epic's edges, each with its reason — then triggers `wsjf-scoring.js`. One session does the whole assessment, running the context, validate and apply-edges commands itself; apply-edges validates the proposal again and writes nothing unless it passes, and a proposal that does not validate stops the run, naming the Epic and each finding. Every edge records the architecture view checked for the decision it orders, and an edge an earlier assessment withdrew is set again only by a proposal that answers the recorded withdrawal reason, so the result does not depend on which Epic was assessed last.
  - `task-dependency-assessment.js` writes build dependencies — Task→Task `blocks` edges — for one Task created outside elaboration (no `elab_key`), and nothing else: it reads that Task, searches the other open Tasks for what it consumes and provides, reads the related ones in full, and writes only that Task's edges, each with its reason — then triggers `wsjf-scoring.js`. One session writes the context, proposes, validates and runs apply-edges; a proposal it cannot make valid stops the run, naming the Task and each finding, and writes nothing. A Task written by elaboration gets its edges from elaboration.
  - `wsjf-scoring.js` reads the edges from beads and never sets one; it judges value, urgency and size only where the source content changed or a value is missing — each Epic from its full PRD, one Epic per session, and each Epic's Tasks in a session per Epic — then recomputes every WSJF over the whole portfolio.
- **Routing & gates** — `route-build.js`, `route-elaboration.js`, `bug-triage.js`, `gate-enforce.js`.
- **Docs** — `ROUTING.md` (how a bead is routed to a composite), `../AGENT-TEAMS-WORKFORCE.md` (the full workforce/pipeline reference).

Workflows are addressed **by name**, never by number.
