# agent-teams-workforce — workflow scripts

These are the **canonical source** for the agent-teams-workforce pipelines: the deterministic `Workflow` scripts that orchestrate the agents in `../agents/`. The agents declare *what* they do; these scripts decide *when* each runs, how work is routed, and where the deterministic control flow ends and agent judgment begins.

## Status: canonical here, deployed by hand (for now)

The Claude Code plugin framework does not deploy workflows natively, so these do not ship to a project automatically the way agents and skills do. Deployment will be **automated** — a `SessionStart` hook will symlink this folder into a consuming project at `.claude/workflows/agent-teams-workforce-pipelines/` and refresh it when the plugin version changes.

Until that automation lands:

- **This folder is the single source of truth.** Edit workflows here, not in a consuming project.
- **Changes must be copied to consuming projects by hand.** A project that already links or copies these scripts will not see an update until you re-copy (or the symlink target is refreshed).

## Contents

- **Composites** — `prd-to-spec.js`, `task-to-deploy.js`, `bug-fix.js`, `infra-change.js`: full pipelines stitched from the pieces below.
- **Front-ends & phases** — `workspace.js`, `prd-reconciliation.js`, `prd-validation.js`, `architecture.js`, `repo-scoping.js`, `trd-authoring.js`, `spec-authoring.js`, `task-decomposition.js`, `tdd-red.js`, `tdd-green.js`, `tdd-refactor.js`, `integration.js`, `adversarial.js`, `deploy.js`, `settle.js`, `documentation.js`, `infra-intent.js`, `story-deploy-fix.js`.
  - `repo-scoping.js` rules the REPO SPAN of a PRD — which repositories its remaining work lands in — after the architecture decision and before anything fans out per repo. The span is an output of the run, recomputed every time and stored nowhere, so a re-run after an adjustment is scoped against the adjustment. The polyrepo-steward maps the greenfield work units onto repositories and creates any repository the work needs that the project does not have; a needed repository is never returned as a human action.
  - `workspace.js` ESTABLISHES the worktree before the first write. Every code-writing composite dispatches it first, and its return value is the sole source of `contract.repoPath` — the caller supplies a repository, this step supplies the worktree. `task-to-deploy.js` and `infra-change.js` key it by the Task's Story, so a Story's Tasks share one worktree and one branch, cut from `main` when its first Task starts.
  - `settle.js` lands a tree in git — commit, push, PR — for `bug-fix.js`, on every exit path after deployment. With `commitOnly` it commits on the branch and stops: `task-to-deploy.js` and `infra-change.js` commit each Task to its Story branch this way, and neither deploys nor opens a pull request.
  - `story-deploy-fix.js` is the one agent step of a Story's deploy, which the host runs when the Story's last Task is done: its scripts check the SSM parameters, `cdk deploy` and verify the stacks, and on a failure this mini has a `cdk-stack-author` fix the Story branch and run the synth assertion tests before the host redeploys. The host then opens the Story's one pull request and waits for GitHub to report it merged.
- **Portfolio** — four workflows over the Epics and Tasks, each runnable alone, sharing `../scripts/portfolio/depscore.py`:
  - `dependency-assessment.js` writes Epic dependency edges — architecture dependencies: which requirements an architecture decision is designed from first — and nothing else — for one new or changed Epic at a time: it reads that Epic's full PRD, searches the other Epics' PRDs for the ones related through an architecture decision the SAD leaves open, reads those in full, and writes only that Epic's edges, each with its reason — then triggers `wsjf-scoring.js`. One session does the whole assessment, running the context, validate and apply-edges commands itself; apply-edges validates the proposal again and writes nothing unless it passes, and a proposal that does not validate stops the run, naming the Epic and each finding. Every edge records the SAD section checked for the decision it orders, and an edge an earlier assessment withdrew is set again only by a proposal that answers the recorded withdrawal reason, so the result does not depend on which Epic was assessed last.
  - `task-dependency-assessment.js` writes build dependencies — Task→Task `blocks` edges — for one Task created outside elaboration (no `elab_key`), and nothing else: it reads that Task, searches the other open Tasks for what it consumes and provides, reads the related ones in full, and writes only that Task's edges, each with its reason — then triggers `wsjf-scoring.js`. One session writes the context, proposes, validates and runs apply-edges; a proposal it cannot make valid stops the run, naming the Task and each finding, and writes nothing. A Task written by elaboration gets its edges from elaboration.
  - `wsjf-scoring.js` reads the edges from beads and never sets one; it judges value, urgency and size only where the source content changed or a value is missing — each Epic from its full PRD, one Epic per session, and each Epic's Tasks in a session per Epic — then recomputes every WSJF over the whole portfolio.
  - `seed-portfolio.js` seeds the portfolio, both halves: it runs `dependency-assessment.js` for every Epic `/seed-portfolio` lists as not assessed since the seeding began, one Epic after another in id order, each with `score: false`, then runs `wsjf-scoring.js` once, without `all` or `rejudge`, over the completed edge set. The first assessment writes the PRD corpus and the rest read it. `/seed-portfolio` checks from the tracker afterwards that nothing is left. An assessment that stops stops the seeding at that Epic, with its findings, and nothing is scored; a seeding is resumed by passing the same `since`, which finishes the edges and then scores.
- **Routing & gates** — `route-build.js`, `route-elaboration.js`, `bug-triage.js`, `gate-enforce.js`.
- **Docs** — `ROUTING.md` (how a bead is routed to a composite), `../AGENT-TEAMS-WORKFORCE.md` (the full workforce/pipeline reference).

Workflows are addressed **by name**, never by number.
