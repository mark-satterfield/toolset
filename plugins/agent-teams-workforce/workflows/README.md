# agent-teams-workforce — workflow scripts

These are the **canonical source** for the agent-teams-workforce pipelines: the deterministic `Workflow` scripts that orchestrate the agents in `../agents/`. The agents declare *what* they do; these scripts decide *when* each runs, how work is routed, and where the deterministic control flow ends and agent judgment begins.

## Status: canonical here, deployed by hand (for now)

The Claude Code plugin framework does not deploy workflows natively, so these do not ship to a project automatically the way agents and skills do. Deployment will be **automated** — a `SessionStart` hook will symlink this folder into a consuming project at `.claude/workflows/agent-teams-workforce-pipelines/` and refresh it when the plugin version changes.

Until that automation lands:

- **This folder is the single source of truth.** Edit workflows here, not in a consuming project.
- **Changes must be copied to consuming projects by hand.** A project that already links or copies these scripts will not see an update until you re-copy (or the symlink target is refreshed).

## Contents

- **Composites** — `task-to-deploy.js`: the build pipeline stitched from the pieces below. It runs the steps the Task's step journal lists, from the first that is not done: one function per step kind, each handed the artifacts earlier steps recorded and returning its own artifacts and the steps its result adds. The step kinds and the up-front plan are defined in `../skills/pipeline-contracts/schemas/pipeline-steps.json`; the journal helper every such script carries is `../scripts/shared-blocks/step-journal.js`. The pipeline's driver dispatches it with `journal: { path, run }` and applies the `STEP-JOURNAL` lines it logs (`../orchestrator/core/journal_lines.py`). Elaboration, `prd-to-spec`, is not a workflow script: it runs in the Python orchestrator (`../orchestrator/run.py`, its steps in `../orchestrator/flows/`), which the pipeline's driver starts; `../orchestrator/specs/epic/` describes it.
- **Front-ends & phases** — `workspace.js`, `prd-creation.js`, `prd-validation.js`, `suite-run.js`, `tdd-red.js`, `tdd-green.js`, `tdd-refactor.js`, `adversarial.js`, `deploy.js`, `settle.js`, `documentation.js`, `infra-intent.js`, `deploy-mechanism.js`, `story-deploy-fix.js`, `built-version.js`.
  - `workspace.js` ESTABLISHES the worktree before the first write. Every code-writing composite dispatches it first, and its return value is the sole source of `contract.repoPath` — the caller supplies a repository, this step supplies the worktree. `task-to-deploy.js` keys it by the Task's Story, so a Story's Tasks share one worktree and one branch, cut from `main` when its first Task starts. A reused tree is left as it is: a restarted build continues on it.
  - `settle.js` lands a tree in git — commit, push, PR. With `commitOnly` it commits on the branch and stops: `task-to-deploy.js` commits each Task to its Story branch this way, after a final `suite-run.js` exits 0, and neither deploys nor opens a pull request.
  - `suite-run.js` runs the one test command the repository declares (its `AGENTS.md` or `CLAUDE.md`, or its Taskfile `test` task) and returns the exit code and the failing tests. `task-to-deploy.js` resolves it once at its baseline step and judges Red, Green, Refactor and the commit by it.
  - `tdd-red.js`, `tdd-green.js` and `documentation.js` each run one agent of their kind when the caller names it (`testAgent`, `only`, `assignment`), and name the agents without running any (`plan`, `select`, `auditOnly`); `task-to-deploy.js` calls them that way, one journal step per agent.
  - `deploy-mechanism.js` and `story-deploy-fix.js` are the agent steps of a Story's deploy, which the host runs when the Story's last Task is done. First a polyrepo-steward rules what the Story's repository publishes (a package to CodeArtifact, with the publish command the repository declares) and deploys (with CDK); the host stops a repository that does neither. Its scripts publish the package, then check the SSM parameters, `cdk deploy` and verify the stacks; on a failure `story-deploy-fix.js` has a `deploy-failure-fixer` fix the Story branch, reads what the fix changed from git, runs the synth assertion tests and commits the fix before the host tries again; a fix that changes no file stops the deploy, and a failure after three fixes stops it. Once the deploy verifies, the host runs `built-version.js`: a `built-architecture-comparer` compares the Story branch's code with the approved architecture and design headings that describe the stacks and entries the Story's Tasks state (`atw-matrix built --story`, then `atw-matrix story-scope` for each stack); a Story whose Tasks state nothing is not compared, writes each difference to `built/<element>/`, and the `architecture-maintainer` corrects the effective version from it before the built views are removed. `story-deploy-fix.js` and `built-version.js` run as the child steps of the Story's `deploy:fix` and `deploy:built-version` journal steps and report each child step to the Story's step journal, so a restarted run begins at the first child step that is not done. The host then opens the Story's one pull request, sets what the Story built verified in the matrix once every check on its head commit passes, and waits for GitHub to report it merged.
- **Portfolio** — three workflows over the Epics and Tasks, each runnable alone, sharing `../scripts/portfolio/depscore.py`:
  - `dependency-assessment.js` writes Epic dependency edges — architecture dependencies: which requirements an architecture decision is designed from first — and nothing else — for one new or changed Epic at a time: it reads that Epic's full PRD, takes the Epics the matrix relates to it (`atw-matrix related --epic`), reads in each related PRD only the requirement headings that bear on an architecture decision the effective architecture leaves open, and writes only that Epic's edges, each with its reason — then triggers `wsjf-scoring.js`. The workflow writes the plan and the context, one session proposes the edges and checks its proposal with the validate command, and the workflow accepts the proposal, validates it and runs apply-edges; apply-edges validates the proposal again and writes nothing unless it passes, and a proposal that does not validate stops the run, naming the Epic and each finding. An accepted proposal is saved with a receipt of the inputs it was made from, and a rerun in the same work directory with unchanged inputs starts no session. Every edge records the architecture view checked for the decision it orders, and an edge an earlier assessment withdrew is set again only by a proposal that answers the recorded withdrawal reason, so the result does not depend on which Epic was assessed last.
  - `task-dependency-assessment.js` writes build dependencies — Task→Task `blocks` edges — for one Task created outside elaboration (no `elab_key`), and nothing else: it reads that Task and the open Tasks the matrix relates to it through the stacks and entries it names (`atw-matrix work`, `atw-matrix deps`), and writes only that Task's edges, each with its reason — then triggers `wsjf-scoring.js`. The workflow writes the plan and the context, one session proposes the edges and checks its proposal with the validate command, and the workflow accepts the proposal, validates it and runs apply-edges; a proposal that does not validate stops the run, naming the Task and each finding, and writes nothing. A Task written by elaboration gets its edges from elaboration.
  - `wsjf-scoring.js` reads the edges from beads and never sets one; it judges value, urgency and size only where the source content changed or a value is missing — each Epic from its full PRD, one Epic per session, and each Epic's Tasks in a session per Epic — then recomputes every WSJF over the whole portfolio.
- **Routing & gates** — `route-build.js`, `route-elaboration.js` (it rules that a bead is elaboration work and names `prd-to-spec`; it dispatches nothing), `gate-enforce.js`.
- **Docs** — `ROUTING.md` (how a bead is routed to a composite), `../AGENT-TEAMS-WORKFORCE.md` (the full workforce/pipeline reference).

Workflows are addressed **by name**, never by number.
