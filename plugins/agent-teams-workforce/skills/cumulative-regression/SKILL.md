# Cumulative regression assurance

A passing command proves only what actually ran. It does not establish that the suite covers all current requirements of the changed component. New feature tests supplement the existing valid behavior; they do not replace it.

## Establish the affected requirements

Read the caller's actual Task, spec, PRD, architecture/contracts, repository instructions and existing tests, plus the prior `.agent-workforce/regression.json` in the assigned repository. Follow component and producer/consumer references to current requirements in other PRDs and affected repositories. Use the supplied documentation locator and supported vault access where applicable. Scope discovery to demonstrated component/dependency impact; do not construct speculative fleet-wide infrastructure. Regression impact links are evidence relationships, never permission to create or change Epic blocker edges. Epic Beads dependencies govern architecture development order; they do not define build, deploy or runtime order.

Record changed components with actual repository-relative files, source references searched and evidence. A source reference identifies a real document and requirement or section, not a paraphrase. Requirement IDs are source-qualified so equal local IDs in different PRDs cannot collide. Do not assume that the newest PRD contains all obligations, that no ledger means greenfield, or that existing tests exhaust the requirements. Missing or inaccessible sources are explicit gaps; `priorRequirementsSearched` must reflect an actual search, and `greenfield` requires evidence that the component has no prior valid obligations.

Carry forward every still-valid prior requirement. Supersession requires an explicit accepted requirement or owner decision reference that authorizes the replaced behavior, with the old requirement ID and reason. Neither a new test, changed implementation, assessor preference nor failing old test authorizes supersession. Preserve unaffected tests and assertions. Renames, relocation or consolidation retain equivalent behavioral coverage and an explicit old-to-new test mapping; removal, weakening or newly skipping a test requires source-backed supersession or a demonstrated equivalent replacement.

## One shared artifact contract

Use the exact schema supplied by the workflow and write one candidate artifact, returning its reference under the artifact-handoff contract. The assessment contains `components`, `discovery`, `sourceFiles`, `requirements`, `mappings`, `replacements` and `runs`. List absolute physical source file paths in `sourceFiles`, including vault note backing files; retain section citations separately. The workflow fingerprints the actual bytes before reuse and binds approval to those bytes. Changed source evidence requires reassessment; a stable path or remembered review is not freshness evidence. Each requirement supplies its `sourceRef`, `componentIds`, `repoPath`, `impacted`, `impactReason`, `applicability` and any `supersedes` records. Preserve all still-valid prior requirements and mappings; mark which this change impacts with concrete reasons. Unaffected retained requirements do not trigger an unnecessary fleet-wide execution sweep. A real behavioral change cannot be waved through by marking every requirement unaffected. Assess unit, contract, integration and nonfunctional applicability explicitly: mark required layers and cite source-backed reasons for exclusions. Cross-service API/event/data interactions normally require contract and integration evidence; repository-local unit coverage alone does not establish these interactions. Do not invent a layer obligation with no applicable behavior.

Before Red, establish requirements and layer applicability; mappings and run definitions may still be incomplete. After Red, finalize mappings to actual tests and declared commands without silently changing the approved requirement/component scope. Each mapping records `requirementId`, `kind`, `runId` and exact `testIds`. A legitimate test rename or consolidation adds `replacements` with `requirementId`, `kind`, `oldTestId`, mapped `newTestIds` and a concrete equivalence `reason`; independent review verifies the old assertion semantics remain covered. Test replacement is distinct from requirement supersession. Each run records its explicit repository, existing supported command and fresh JUnit XML report path under that repository’s `.agent-workforce/reports/`. JUnit test IDs use the exact `classname::name` values emitted by that runner. One test may substantiate several requirements only when its actual assertions cover each; file names or collection counts alone are not behavioral evidence.

## Test authoring and execution

When given `regressionPlanPath`, read that artifact and the cited requirement sections before editing. Extend existing tests for the assigned layer, preserving valid assertions from earlier PRDs. Add missing regression assertions for affected current requirements along with the new feature tests. Existing behavior tests normally remain green during Red; only genuinely new/unimplemented behavior must fail for its intended reason. Do not rewrite sound tests merely to manufacture Red.

Use repository-supported test commands and reporting configuration; do not narrow the whole-suite gate to only the new tests, omit failing tests, or rewrite expected behavior to match the implementation. Report unsupported or unavailable execution/reporting capabilities explicitly. The deterministic gate executes the declared runs and checks fresh report results; an agent's `passed`, a stale report, an exit code alone, a skipped/disabled test, or an unmapped green suite is insufficient. Cross-repository impacts need mapped execution evidence in the owning repository; inaccessible dependencies remain gaps rather than assumed passes.

## Independent review

Reviewers read source requirements, relevant code/contracts, the prior ledger, changed test assertions and current mappings. Check omissions as well as listed entries: changed components missing prior obligations, required layers missing mappings, mapped IDs absent from actual tests, unjustified test removal/weakening/skips and unsupported supersession. Report concrete findings with source references and a verifiable correction. Do not edit the producer's artifacts or approve your own assessment. The workflow retains the accepted cumulative ledger only after independent approval and deterministic execution evidence; unresolved gaps prevent completion.
